# Improve an existing game

Start with the actual current scene and the user's requested scope. Separate whole-scene redesign, small art fixes, rules changes, content expansion and engine migration. A general request to improve visuals does not override a specific request to retain an accepted style.

## Variable state and artwork

The Signal Harbor case began with a lighthouse image depicting two fixed slots. Larger capacities pushed lights over the roof. The useful abstraction was a top, repeatable slot and bottom, with rendering, hints and hit areas sharing coordinates. Review extremes before producing fixed artwork. Do not infer that every game needs procedural illustration.

## Existing players

Preserve stable game IDs, storage keys and save formats when promised. Exercise a real old save through normal upgrade, not a newly generated approximation alone. Validate malformed saves without overwriting recoverable data. Reordered content needs stable identity rather than positional indexes.

## Player integration

The Star Triad case needed separate changes to the game viewport, player safe area and library cover. A new game build does not automatically replace a cover or player shell. Diagnose the affected layer and verify through the intended entry point. A desktop prototype does not prove app delivery.

## Scope before research

When the task can mean faithful reference difficulty or original content, settle that promise before deep generation work. Original design may choose explicit new parameters. Reference matching requires provenance and uncertainty. Cases report historical outcomes; they are not a claim that all branches are automated.
